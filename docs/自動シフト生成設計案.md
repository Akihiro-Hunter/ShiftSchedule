# 自動シフト生成 設計案

作業ごとの必要人数と職員の可能作業・契約日数をもとに、勤務表を自動生成し、人手不足の日と作業を見える化する。
現時点では設計のみ（未実装）。

## 1. 前提条件（相談で確定した内容）

### 必須の条件

1. 可能作業のない作業には入れない
2. 同じ時間帯に複数の作業には入れない
3. 作業ごとの必要人数（日別の上書きあり）。満たせない場合は「不足」として報告し、契約日数は破らない
4. 契約勤務日数（週3〜6日）を超えない。週は月曜〜日曜で数え、半月や月をまたぐ週は前後の勤務を通算する

### 努力目標（できれば満たす）

5. 休み希望の日は出さない
6. 7連勤以上を避ける
7. 契約勤務日数を下回らない
8. 作業ごとの必要人数を満たしたうえで、余りは予定人数まで自由に配置する
9. 休みの偏りを減らす

### 必要人数の例（倉庫）

| 時間帯 | 作業 | 必要人数 | 種別 |
|---|---|---|---|
| 仕分け作業（作業開始） | ドライ | 10人以上 | 必須 |
| 仕分け作業（作業開始） | クール、ネコポス、リフト | 各1人以上 | 必須 |
| トラック積込（仕分け後） | 各トラック | 1人ずつ（足りなくても可） | できれば |
| 日時指定保管（8時以降） | 各作業 | 各2人以上 | 必須 |

- 繁忙期は日別・期間別に上書きできる（例：リフト2人以上、ドライ指定日仕訳3人以上）。
- 1人が複数の時間帯に入れる。将来は設定で「1人1時間帯のみ」などに切り替えられるようにする。
- 将来は他業種（飲食店、教育、サービスなど）にも対応する。倉庫専用の作りにしない。

### 将来の拡張（今回は空けておく）

- 資格条件（「リフトができる人がいないと成立しない」「乙4の資格者がいないと誰も働けない」など）
- 職員ごとの勤務可能時間帯（早上がりなど）

### 人手不足の扱い

- 契約日数は必ず守り、足りない分は不足として報告する。
- 予定人数を下回る日は強調表示する。マネージャーが「この日は来られる人は来て」と募集できるようにする。
- 作業ごとの必要人数の合計が予定人数を超える日は、「人手不足の可能性」として表示する。

## 2. 全体像

```
[マスタ]               [条件]                 [生成]                 [結果・確認]
時間帯・作業      →  必要人数ルール     →  自動生成エンジン   →  勤務表(割り当て)
職員の可能作業        日別の上書き           (OR-Tools CP-SAT)      不足の日一覧
契約日数・休み希望    予定人数(既存)
```

## 3. データ構造

### 既存を活かすもの

- `TaskGroup`（大項目）は「時間帯（フェーズ）」に相当する（仕分け、積込、日時指定保管。他業種ではランチ、ディナーなど）。
- `WorkTask`（作業）、`Account` の可能作業、`DailyPlan`（予定人数）、`ShiftEntry`（出勤・休み）、休み希望、契約日数はそのまま使う。

### 新規テーブル

| テーブル | 主な列 | 役割 |
|---|---|---|
| `task_requirements` | task_id, min_count, kind（必須/できれば）, weight | 作業ごとの既定の必要人数 |
| `task_requirement_overrides` | task_id, 開始日, 終了日, min_count | 日別・期間（繁忙期）の上書き |
| `shift_assignments` | account_id, work_date, task_id | 誰がいつどの作業に入るか |

- `shift_assignments` は職員×日×作業で1行とし、1人が複数の時間帯に入れることを前提にする。
- 「1人1時間帯のみ」「1日の上限数」は、後から設定テーブルを追加して制御する。
- 必要人数は、既定値を引き、上書きがあればその日はそちらを使う。
- 資格条件は、後から `task_prerequisites` のようなテーブルで追加できるように、今回は設けない。

## 4. 画面

1. **作業項目画面（既存）**
   - 作業名に加えて、各作業の「必要人数（既定）」と「必須/できれば」を入力できる欄を足す。
   - 今の2列レイアウトに合わせる。
2. **繁忙期の設定（新規）**
   - 「期間・作業・人数」を一覧で登録する（例：11/20〜12/25 リフト2人）。
3. **勤務表（既存）の拡張**
   - 日ごとの割り当て（どの作業か）を表示・手修正できるようにする。
   - 出勤人数が予定人数を下回る日を強調する。
   - 日付をクリックすると、不足している作業（「リフトが1人不足」など）を表示する。
4. **不足日の一覧（新規）**
   - 募集の材料として、不足している日と作業をまとめて表示する。

## 5. 自動生成（エンジン）

**ライブラリ:** Google OR-Tools の CP-SAT。Maven で追加する。Java 版が Spring Boot 4 の環境で動くかは、導入前に小さな試作で確認する。動かない場合は Timefold を代替とする。

**変数:** 職員×日×作業ごとに0/1（入る/入らない）を持つ。出勤日かどうかは、そのいずれかが1の日とする。

### 必須の制約（破らない）

- 可能作業のない作業には入れない。
- 週（月曜〜日曜）の出勤日数は契約日数以下。前後の半月の確定済みの勤務を通算する。
- ロック済みの人・日、確定済みの半月は動かさない。

### 努力目標（減点で調整）

| 項目 | 重みの目安 |
|---|---|
| 必要人数（必須）の不足 | 非常に大 |
| 休み希望の日に出勤 | 大 |
| 必要人数（できれば）の不足 | 中 |
| 7連勤以上 | 中 |
| 契約日数を下回る | 小 |
| 予定人数に届かない | 小 |
| 休みの偏り | 小 |

重みは設定ファイルにまとめ、結果を見ながら調整できるようにする。

### 実行の流れ

- 勤務表画面の「自動生成」ボタンで半月分を生成する。
- 生成結果は確定せず、下書きとして表示する。
- マネージャーが手修正して確定する。
- 解く時間に上限（例：30秒）を設け、時間切れならその時点の最良の解を使う。

## 6. 作る順番（段階）

| 段階 | 内容 | できること |
|---|---|---|
| 1 | 必要人数の設定（既定・必須/できれば）と、作業項目画面の入力欄 | 設定を保存できる |
| 2 | 日別の上書き（繁忙期） | 日ごとの必要人数が決まる |
| 3 | 割り当てテーブルと勤務表での表示・手修正、不足の強調と一覧 | 手動運用でも不足が分かる |
| 4 | OR-Tools の導入と自動生成（必須の制約のみ） | 条件を満たす勤務表が出る |
| 5 | 努力目標（休み希望、連勤、偏り）と重みの調整 | 質の高い割り当てになる |
| 6 | 資格条件、勤務可能時間帯 | 他業種・拡張対応 |

段階3までで「この日は何が足りないか」が見えるようになる。自動生成は段階4から。

## 7. リスクと確認事項

- **OR-Tools の導入:** 動作確認は段階4の前に試作で行う。
- **`ShiftEntry` との整合:** 出勤の有無は `ShiftEntry`、どの作業かは `shift_assignments` と役割を分け、片方だけが変わる状態を防ぐ。
- **予定人数との関係:** 既定値は月・火13人、他は15人。作業ごとの必要人数の合計がこれを超える日は、予定人数を超えた必要として表示する。
- **週をまたぐ未確定の半月:** 前の半月が未確定の場合は、確定済みの分だけを数え、その旨を表示する。
